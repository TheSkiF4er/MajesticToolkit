# MajesticToolkit 2.3.8 — Облачные файлы и доказательства
> **Архив релиза.** Здесь сохранены возможности, проверки и ограничения, актуальные на момент выпуска 2.3.8. Полная последовательность изменений — в [истории версий](../CHANGELOG.md).


## Реализованное файловое хранилище

- **SQLite BLOB storage** на существующем Cloud Identity Server: таблицы `cloud_files`, `cloud_file_versions`, `cloud_file_blobs`, `cloud_file_links`. Двоичные файлы хранятся отдельно от версий метаданных и дедуплицируются по SHA-256 в пределах облачного RP-профиля. Каждый файл имеет неизменяемый UUID, авторство, текущую версию и историю изменений. Операции выполняются транзакционно.
- **Локальное Evidence Vault не выгружается автоматически.** В Cloud Files пользователь выбирает конкретный файл из локального Evidence Vault и явно подтверждает передачу. При загрузке сервер проверяет разрешённые MIME и сигнатуру содержимого, размер и SHA-256. Полученный файл также проверяется на клиенте по SHA-256 до записи в локальный Evidence Vault. Локальные исходные файлы не изменяются.
- **Приватность и совместный доступ:** файл создаётся в режиме «Только я», если не выбрана публикация для команды. Viewer может читать общие материалы, Editor и выше — загружать и редактировать общие файлы. Частный файл виден **только автору**, даже администратор команды не имеет доступа к его содержимому через API. Проверка сессии, роли, команды, облачного профиля и авторства выполняется на сервере, включая повторную проверку после получения тела запроса.
- **Версии:** новая загрузка и изменение метаданных создают новую версию, сервер требует `baseVersion` (optimistic locking, HTTP 409). Предыдущие двоичные версии остаются доступными для получения в Evidence Vault. При удалении файла удаляются все редакции и связи, неиспользуемые BLOB очищаются. Параллельные правки разных участников не перезаписываются молча.
- **Вложения:** опубликованный общекомандный файл можно прикрепить к опубликованному материалу Knowledge Center или существующей тактической записи (карте, плану, аирдропу, территории). Проверка существования цели и прав выполняется внутри серверной транзакции. Привязки доступны в Cloud Files, при удалении файла удаляются вместе с ним. Для возврата в приватный режим сначала нужно открепить все ссылки.
- **Безопасная доставка:** байты передаются прямым HTTPS (или разрешённым localhost HTTP) через фоновый процесс расширения без вывода access/refresh-токенов в страницу. Сервер скачивает в режиме `Content-Disposition: attachment`, `nosniff`, CSP `sandbox` и `Cache-Control: no-store`. Клиент контролирует поток и контрольную сумму. Загрузка файлов через JSON/base64 API не предусмотрена.

## Использование

1. На существующий **полный** проект 2.3.7 распакуйте файлы 2.3.8, сохраняя структуру каталогов.
2. Запустите `npm run cloud:identity` (Node.js 22). Прежняя SQLite-база автоматически получает новые таблицы, аккаунты и команды не сбрасываются. Сделайте резервную копию до обновления. Публичному серверу обязателен TLS.
3. В Team & Cloud войдите в аккаунт, выберите команду и привяжите локальный RP-профиль к серверному профилю.
4. Добавьте документ, изображение или видео в **локальный Evidence Vault**. В блоке **Cloud Files & Evidence** выберите этот файл и уровень доступа: «Только я» или «Вся команда». Нажмите «Явно загрузить выбранный файл».
5. Пользователи команды могут получить общие файлы в локальный Evidence Vault (включая исторические версии). Редакторы могут загрузить новую версию, изменить метаданные, создать/удалить ссылку на опубликованный документ или тактическую запись; изменения проходят контроль версий.

## Квоты и границы

- Максимальный размер файла — 32 МиБ, суммарный объём уникальных версий в одном облачном RP-профиле — 256 МиБ. Максимум 500 файлов, 100 версий и 25 ссылок на файл. Разрешены PNG/JPEG/GIF/WebP, PDF, TXT, MP4/WebM, DOCX/XLSX. Потенциально исполняемые/встраиваемые форматы (HTML/SVG/JS/EXE) не принимаются.
- Облачные файлы **не попадают в Evidence Vault и судебные дела на других устройствах автоматически**: импорт всегда явный. Пользователь должен самостоятельно обеспечить правомерность передачи данных. Ссылка на материал не предоставляет доступ к его черновику.
- Сканирование файлов антивирусом, отдельное S3-хранилище, репликация, сборка Apple и публичная HTTPS-нагрузочная приёмка **не выполнены**. Хранение использует SQLite на том же сервере. Резервное копирование должно учитывать SQLite WAL/SHM (рекомендуется online backup API). Следующая версия roadmap — 2.3.9 Cloud Operations & Reliability.

## Проверки

- `node --test tests/cloud-files-238.test.mjs` — реальные HTTP/SQLite-тесты на нескольких аккаунтах, приватность, контроль прав, версионирование, SHA-256, ссылки, отзыв сессии, рестарт и удаление.
- `python3 tests/browser-cloud-files-238.py` — Chromium DOM-проверка экрана Cloud Files & Evidence с изолированным RPC-адаптером.
- `npm run verify` — полная регрессия, четыре браузерные сборки и проверка релизных ZIP/SHA-256.

Автоматические тесты не заменяют тестирование установленного браузерного расширения и реального публичного HTTPS-сервера в production-конфигурации.
