# MajesticToolkit 2.3.3 — Cloud Storage & Migration

## Рабочая последовательность

1. Запустите `npm run cloud:identity` с Node.js 22.13+ и стабильным каталогом SQLite. Для удалённых клиентов используйте **публично доступный HTTPS-сервер с прямым TLS**, как описано в `RELEASE_NOTES_2.3.1.md`. Сервер не появляется автоматически при установке расширения.
2. Откройте **Team & Cloud**, подключите сервер и войдите в аккаунт версии 2.3.1. Вступите в команду или создайте её средствами 2.3.2.
3. Owner или Admin выбирает локальный RP-профиль и создаёт облачный профиль команды. Если профиль с этим названием уже существует и совпадает RP-проект и сервер, его ID возвращается повторно без дублирования. В команде допускается до 100 профилей.
4. Любой участник может выбрать локальный RP-профиль и привязать его к существующему облачному профилю **того же проекта и сервера**. Маппинг хранится только на устройстве, с изоляцией по адресу сервера, аккаунту, команде и ID локального профиля. Локальные RP-профили не переименовываются и не удаляются.
5. Owner, Admin или Editor отмечает нужные **семьи** и **организации** в форме и подтверждает передачу. Расширение проверяет локальные записи через прежние семейные/организационные хранилища и загружает выбранные записи батчами через доверенный background. Отказ сети сохраняет уже подтверждённые батчи, а повторная отправка совпадающих данных безопасна.
6. Участники команды с любой ролью видят серверные записи в Team & Cloud. API `GET /v1/teams/:teamId/cloud/profiles/:profileId/records` возвращает полные записи, включая нормализованный облачный `profileId`, SHA-256, версию и время импорта. При большом количестве записей применяется пагинация `after` и опциональный фильтр `kind=family|organization`.
7. Перенос не изменяет и не удаляет локальные записи. Для проверки импорта из другого браузера войдите в тот же сервер и команду и просмотрите облачный профиль; привязка локального профиля на втором устройстве настраивается отдельно.

## Реальный серверный механизм и ограничения

- Модули: `cloud-identity/server.mjs`, `cloud-identity/teams.mjs`, **`cloud-identity/storage.mjs`**. Последний создаёт SQLite-таблицы `cloud_profiles`, `cloud_records` с внешними ключами, уникальностью по команде/профилю/типу/ID, транзакциями `BEGIN IMMEDIATE`, SHA-256 контрольными суммами и каскадным удалением при удалении команды.
- `POST /v1/teams/:teamId/cloud/profiles` доступен только Owner/Admin. Импорт записей `POST /v1/teams/:teamId/cloud/profiles/:profileId/records` доступен Owner/Admin/Editor. Чтение — всем членам команды. Перед каждой записью сервер повторно проверяет живую сессию и роль *внутри транзакции*. Посторонние получают 404 без раскрытия существования команды или RP-профиля.
- Семейные и организационные данные повторно проходят **исходные доменные валидаторы** `cleanFamily/validateFamilies`, `cleanOrganization/validateOrganizations`. Сервер назначает облачный `profileId` самостоятельно, игнорируя клиентскую попытку определить командный namespace. Допустимые типы ограничены `family` и `organization`; дополнительные конфиденциальные данные, файлы, карты, жалобы, Evidence Vault и AI-подключения не загружаются автоматически.
- Повторный импорт того же ID с точно такими же нормализованными данными возвращает `unchanged` без дублирования. Если ID уже существует с другим содержимым, HTTP 409 отклоняет весь батч и **не перезаписывает** серверную запись. Каждая операция проверяется по реальной SQLite, в том числе после перезапуска процесса. Разрешение конфликтов и двусторонняя синхронизация относятся к 2.3.4.
- За один запрос не более 20 записей и 512 КиБ; размер нормализованной записи до 160 КиБ, общий лимит 10 000 записей на облачный профиль. Расширение разбивает перенос на батчи и сообщает о уже успешных перед сбойным батчах. Веб-интерфейс показывает первые 250 локальных записей и первую страницу из 20 облачных записей, API позволяет постраничное чтение остальных.
- SQLite содержит **все данные в открытом виде для администратора сервера**: при размещении на чужом сервере считайте участников с правом чтения и оператора сервера доверенными. Реальное публичное размещение требует TLS, защиту файлов SQLite/WAL, регулярные резервные копии и контроля доступа к серверу. Шифрование данных на стороне клиента не реализовано.
- Новые облачные таблицы создаются автоматически при старте существующего сервера 2.3.2. Backup v21 остаётся локальной резервной копией и не заменяется командным импортом. Автоматическая многопользовательская синхронизация, уведомления, онлайн-редактирование, удалённая правка уже импортированных записей и облачные бинарные файлы не входят в 2.3.3.

## Проверка

```sh
node --test tests/cloud-storage-233.test.mjs tests/cloud-teams-232.test.mjs tests/cloud-identity-231.test.mjs
python3 tests/browser-cloud-storage-233.py
npm run verify
```

В интеграционных тестах проверяются реальный HTTP-сервер/SQLite, миграция, повторный импорт, защита от конфликта, сохранение после перезапуска, запрет записи Viewer и постороннего пользователя, отзыв сессий, исключение участника, каскадное удаление команды и background-клиент. Browser smoke проверяет выбор записей, привязку/отвязку и отсутствие изменений локального хранилища. Проверка установленного расширения на публичном HTTPS-сервере и нагрузочные испытания остаются задачами production-развёртывания.
