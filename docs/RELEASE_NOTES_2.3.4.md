# MajesticToolkit 2.3.4 — Синхронизация устройств и работа без сети
> **Архив релиза.** Здесь сохранены возможности, проверки и ограничения, актуальные на момент выпуска 2.3.4. Полная последовательность изменений — в [истории версий](../CHANGELOG.md).


## Установка и включение

1. Примените изменённые файлы поверх **полного** проекта версии 2.3.3 и запустите `npm run verify` (Node.js 22). Для реальной работы запустите постоянно доступный `npm run cloud:identity` с сохранением SQLite-файла на постоянном диске, прямым TLS для внешнего адреса и защищённым доступом к файлам базы/WAL.
2. При запуске сервера `installCloudSync()` безопасно добавляет `cloud_records.deleted_at` и создаёт SQLite-журнал `cloud_changes`. Все действующие записи, импортированные ранее через 2.3.3, попадают в журнал; данные аккаунтов, команд и RP-профилей не сбрасываются.
3. На каждом устройстве войдите в Cloud Identity Server, вступите в одну команду и привяжите локальный RP-профиль к **одному и тому же облачному** профилю команды (проект и сервер должны совпадать). У каждого устройства может быть свой локальный ID профиля.
4. В разделе Team & Cloud выберите привязку и нажмите **«Включить синхронизацию»**. Подтвердите передачу: **все семьи и организации данного локального профиля станут доступны участникам команды**, а не только записи, ранее выбранные для ручного импорта. По умолчанию синхронизация **выключена**.
5. Синхронизация происходит после изменений в `browser.storage.local` и по фоновому alarm с интервалом ~1 минута. Доступны «Синхронизировать сейчас», «Отключить», счётчик ожидающих записей и ошибок/конфликтов. Скорость доставки зависит от состояния браузера, сети и сервисного процесса.
6. При выключении синхронизации локальные записи и ещё не отправленная очередь **остаются локальными**. Повторное включение продолжает работу с тем же удалённым RP-профилем.

## Серверное поведение

- `GET /v1/teams/:teamId/cloud/profiles/:profileId/sync/snapshot?after=...&watermark=...&limit=100`: согласованный начальный снимок существующих и удалённых записей на фиксированном курсоре журнала. При постраничном чтении нужно передавать возвращённый `watermark`.
- `GET .../sync?after=<seq>&limit=100`: инкрементальный, упорядоченный поток изменений, версии и метки удаления.
- `GET .../sync/record/:kind/:id`: последняя версия для ручного разрешения конфликта.
- `POST .../sync`: одна операция `{operationId,kind,id,baseVersion,record}` либо `{operationId,kind,id,baseVersion,deleted:true}`. Сервер выполняет её внутри `BEGIN IMMEDIATE` и повторно проверяет команду, роль и сессию. При несовпадении версии — HTTP 409 без потери старого содержимого. Повтор того же `operationId` с тем же содержимым возвращает прежний результат; использование ID для другой записи отклоняется.
- GET разрешён Viewer/Editor/Admin/Owner, POST — Editor/Admin/Owner. Удалённый из команды клиент получает 404, отозванная сессия — 401. Данные других команд изолированы.
- Данные сериализованы и проверяются прежними доменными валидаторами семей и организаций. Удаления сохраняются как tombstones, чтобы офлайн-клиенты не воскрешали записи.

## Разрешение конфликтов и офлайн

- Очередь и точки подтверждения хранятся только в доверенном `storage.local` расширения, отдельно по origin, аккаунту, команде и локальному RP-профилю. Невыполненная операция сохраняет UUID и исходную серверную версию; после сетевой ошибки/перезапуска повторяется с тем же UUID. Очередь ограничена порциями по 25 записей, последующие изменения захватываются следующими проходами.
- Сервер никогда не выполняет принудительное «последний записавший победил». При двух изменениях одной записи создаётся явный конфликт. «Взять облачную» заменяет локальную запись с повторной валидацией целостности. «Оставить локальную» ставит новую условную запись поверх **текущей** удалённой версии; если она изменится повторно, снова появится конфликт.
- Облачное удаление не обходит локальные ограничения: если у записи есть журнал действий или зависимые ссылки, она сохраняется и поднимается конфликт. Пользователь должен сначала безопасно архивировать или устранить связи. Если удалённый RP-профиль отсутствует локально, синхронизация останавливается вместо массовой отправки удалений.
- Локальная очистка токенов или удаление устройства не стирает серверные данные. Смена привязки во время включённой синхронизации запрещена. Выход из аккаунта не сбрасывает локальный исходящий журнал.

## Границы версии

- Реплицируются только **семьи и организации** привязанного RP-профиля. Tactical Toolkit, финансовый реестр, файлы, Evidence Vault, AI, ссылки и настройки остаются локальными. Это не общий cloud-backup и не live co-editing курсоров.
- При отключении сервера чтение/редактирование локальных записей остаётся доступным; нельзя гарантировать доступность облачных записей, ещё ни разу не загруженных на устройство.
- Локальная база и серверное SQLite-хранилище не имеют end-to-end encryption: операторы сервера и участники команды с правами чтения имеют доступ к командным записям. Нужно обеспечивать защищённое хранилище, TLS, резервное копирование и ротацию учётных данных.
- Автоматическая синхронизация не отменяет `Backup v21`. Проверка реальных установленных расширений на целевых платформах и длительная нагрузочная приёмка необходимы перед объявлением сервиса GA.

## Тестирование

```sh
node --test tests/cloud-sync-234.test.mjs tests/cloud-storage-233.test.mjs tests/cloud-teams-232.test.mjs
npm run verify
```

Тесты покрывают две независимые установки клиента, постоянство сервера SQLite, начальный снимок и курсоры, сравнение версий и защиту от повторов, ограничения RBAC/сессий, офлайн/возобновление, разрешение конфликта в обе стороны, метки удаления и защиту от удаления локального RP-профиля.
